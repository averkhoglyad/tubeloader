# PR review protocol

Протокол для агента, ревьюящего MR в CI-пайплайне: роль, оси, верификация, формат результата.

## Контекст проекта

Стек и его ограничения — `docs/tech-stack.md`; версии — `gradle/libs.versions.toml`.

## Роль и границы

- Ревьюер проверяет MR и выносит вердикт: approve или changes requested со списком находок.
- Read-only по коду: правки не вносит.

## Оси ревью

- **STANDARDS** — корректность, качество кода, соответствие стандартам репо.
- **SPEC** — соответствие изменения спеке фичи и архитектурным инвариантам.

Тикет сверяется, только если он передан в описании MR.

## Верификация

- Каждая находка — с `path:line` и доказательством: вывод grep, цитата из спеки или ADR.
  «Выглядит нормально» без доказательства не является вердиктом.
- Отсутствие поведения X — не дефект, а находка-плейсхолдер (`unsure:`), когда X вне
  согласованного объёма спеки фичи; иначе — дефект.

## Буквальность согласования

- Диф сверяется с формулировками спеки и тикета, на которые ссылается MR. Самовольное
  «упрощение» или «улучшение» согласованного поведения — находка.
- Если тест расходится со спекой: сначала перечитать согласованное решение; правится тест,
  а не код, если код соответствует спеке. Расхождение фиксируется в вердикте явно.

## Формат находки

- `[path:line](url) — <проблема>. <фикс>.`
- Префикс серьёзности: `bug:` / `risk:` / `nit:` / `unsure:`.
- Без построчной похвалы; обоснование решения — на уровне MR.
- Точные символы — в бэктиках; фикс — конкретный, не «рассмотреть рефакторинг».
- Не пересказывать дифф.

## Источники

Карта канонических мест — `checklist.md` рядом. Содержание читается по ссылке, здесь не пересказывается.
