# Domain docs

Как навыки работают с доменной документацией этого репозитория.

## Что читать перед исследованием

- **`CONTEXT.md`** в корне — глоссарий проекта.
- **`CONTEXT-MAP.md`** в корне, если существует: указывает на `CONTEXT.md` по контекстам. Читать
  каждый, относящийся к теме.
- **`docs/adr/`** — ADR, затрагивающие область работы.

Файлы создаются лениво, навыком `/domain-modeling`. Если их нет — работать молча: не сообщать
об отсутствии и не предлагать создать заранее.

## Раскладка

Single-context:

```
/
├── CONTEXT.md
├── docs/
│   ├── adr/
│   │   └── 0001-<decision>.md
│   ├── agents/          ← конфиг этих навыков
│   └── research/        ← отчёты исследований
└── core/
```

Тикеты и спеки в раскладку домена не входят: спека — `docs/features/<feature>/spec.md` ([specs.md](specs.md)),
тикеты — issue в GitHub ([issue-tracker.md](issue-tracker.md)).

## Использовать словарь глоссария

Называя доменное понятие — в заголовке тикета, предложении по рефакторингу, гипотезе, имени теста —
брать термин из `CONTEXT.md`. Не уходить в синонимы, которые глоссарий помечает как `_Avoid_`.

Если нужного понятия в глоссарии нет, это сигнал: либо язык выдуман и стоит пересмотреть формулировку,
либо это реальный пробел для `/domain-modeling`.

## Конфликты с ADR

Если результат противоречит существующему ADR — сказать об этом явно, а не перекрывать молча.
