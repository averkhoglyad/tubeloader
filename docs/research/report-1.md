# Архитектурный документ: десктоп-приложение для скачивания видео

**Версия:** 1.0 (финальная, верхнеуровневая)
**Статус:** к реализации
**Стек:** нейтральный (маппинг на Kotlin/JVM и Rust — раздел 15)
**Сфера:** ядро загрузки; GUI/TUI — тонкие фронтенды, контрактно

---

## 1. Контекст и цели

**Продукт:** десктоп-менеджер скачивания видео/аудио из множества источников. Минимум: YouTube и Rutube. Целевое качество: отдельные video+audio потоки с муксингом через ffmpeg (прототип муксера существует и работает).

**Существующее состояние:** прототип на JVM (TornadoFX+Kotlin): Rutube-пайплайн живой, YouTube-экстракция мертва из-за эскалации антибот-защиты. Планируется переписывание приложения с заменой GUI-стека.

**Цели архитектуры:**

1. G1 — скачивание из YouTube и Rutube в высоком качестве (video+audio → ffmpeg mux).
2. G2 — **заменяемость реализаций загрузчиков** (первоклассное требование): добавление, подмена и удаление бэкендов без изменений ядра.
3. G3 — живучесть при постоянных изменениях источников: изоляция нестабильного кода, независимое обновление компонентов, восстановление после сбоев.
4. G4 — стек-нейтральное ядро: смена GUI/TUI (Compose, Rust+ratatui/egui, проч.) не затрагивает бизнес-логику.

**Не-цели (осознанно):** маркетплейс плагинов, поддержка «всех сайтов» как продукта, серверный режим, собственный InnerTube-клиент в ядре, универсальный движок «скачать что угодно откуда угодно».

## 2. Ключевые архитектурные решения (ADR)

| # | Решение | Обоснование (кратко) |
|---|---|---|
| D1 | **Headless-ядро + тонкие фронтенды** (команды вниз / события вверх) | Тестируемость без GUI; GUI/TUI/CLI — взаимозаменяемые фронтенды;G4 |
| D2 | **Источники = плагины за контрактом `Backend`**, роутинг по URL | G2; новый источник ≠ правка ядра |
| D3 | **Capability-модель**: `Delegate` (бэкенд качает сам) / `Native` (качает общий пайплайн) / `ResolveOnly` | Не приводит к одному знаменателю принципиально разные бэкенды (yt-dlp vs нативный скрейпер); G2 |
| D4 | **Целевой YouTube-бэкенд — yt-dlp portable-binary в режиме Delegate** | Единственный экстрактор с индустрийной robustness против антибота (decipher/nsig/PO-токены, каденс фиксов — часы/дни против недель/никогда). Альтернативы отклонены: NewPipeExtractor — GPL (стопор closed source), JavaTube/pytube — bus factor/мертвы, YoutubeExplode — .NET-only, rustypipe — GPL/один мейнтейнер (кандидат на будущее, см. §5.6). Принятые издержки — §5.5 |
| D5 | **Нестабильные экстракторы — в изолированные процессы + собственный канал обновления** | Краш парсера враждебного контента ≠ краш приложения; фикс YouTube ≠ релиз приложения; G3 |
| D6 | **Персистентный job journal + staging + атомарная финализация** | Восстановление очереди после крэша/перезагрузки; в библиотеке никогда не бывает полуфайлов |
| D7 | **Единая нормализация прогресса и ошибок в ядре** | Один UX поверх гетерогенных бэкендов; retry-политики по таксономии, а не «ретрай вообще» |
| D8 | **Contract-тесты на golden-фикстурах для каждого бэкенда** | Предохранитель против дрейфа форматов; проверяемость при замене реализации (G2) |

│ │ YouTube     │ │ │ постпроцессинг        │

│ └─────────────┘ │        │ capability=Native
│ ┌─────────────┐ │

│ INFRASTRUCTURE                                                │
│  ProcessRunner (spawn·sandbox·tree-kill·pump)                 │

```

**Два потока исполнения (ядро поддерживает оба):**

```
Delegate (YouTube, целевой):
  Job → Router → YtDlpBackend.download()
      → [yt-dlp.exe + ffmpeg, изолированные процессы]
      → прогресс (stdout) → нормализация → StagingFS → Finalize(atomic move)

Native (Rutube):
  Job → Router → RutubeBackend.resolve() → ResolvedMedia
      → FormatSelector → Generic Pipeline (HTTP/HLS download)
      → FfmpegService (мукс video+audio) → StagingFS → Finalize
```

## 4. Контракт загрузчика (ядро расширяемости)

```
interface Backend {
  id: string                            // "youtube" | "rutube" | ...
  version: string                       // версия реализации + версия компонента (yt-dlp X.Y)

  capabilities: {
    resolve:    bool                    // умеет отдавать метаданные+манифест
    download:   Delegate | Native | None
    subtitles: bool · live: bool · chapters: bool · login: bool
  }

  urlMatchers: [HostPattern]            // статический роутинг без сети
  canHandle(url): bool                  // опциональная дешёвая проверка

  resolve(url, ctx) → ResolvedMedia
  download(job, selection, sink, ct) → DownloadResult   // обязателен только при Delegate
}

record ResolvedMedia {
  key: SourceVideoKey                   // стабильный идентификатор (дедуп)
  metadata: { title, uploader, duration, thumbnails, chapters }
  streams: [ Stream ]                   // единая модель для всех источников
  subtitles: [ Track ]
  expiresAt: timestamp                  // сроки жизни URL — обязательное поле
}

record Stream {
  kind: Muxed | VideoOnly | AudioOnly
  container, codecs, width, height, bitrate, filesize?
  protocol: Http | Hls | Dash
  url, headers                          // headers обязательны: разные клиенты → разные требования
}
```

### 4.1 Механизм заменяемости (реализация G2)

1. **Anti-corruption слой:** ядро оперирует только `ResolvedMedia`/`Stream`/событиями — модели yt-dlp/Rutube не протекают наружу.
2. **Реестр + статическая регистрация** в точке компоновки (DI). Динамическая загрузка плагинов — не-цель.
3. **Capability-декларация** освобождает ядро от знания, *как* бэкенд качает.
4. **Golden-фикстуры на каждый бэкенд** (§14): записанные входы (JSON `-J`, HTML) + эталонные `ResolvedMedia`. Любая замена/обновление реализации прогоняется через тот же набор — «поведение сохранилось или изменилось осознанно».
5. **Замена — не событие ядра:** новая сборка модуля, регистрация вместо старой, фикстуры зелёные. Ядро не меняется.

### 4.2 Планируемые сценарии подмены

| Сценарий | Действия |
|---|---|
| Обновление/откат yt-dlp | ComponentUpdater (§9.4), бэкенд-код без изменений |
| yt-dlp → нативный экстрактор (если созреет rustypipe/YoutubeExplode-аналог под выбранный стек) | новый Backend с `download: Native` (или `Delegate` со своим скачиванием), тот же контракт |
| Переход YouTube Delegate → Native (L2: yt-dlp только резолвит, качает Generic Pipeline) | смена одного поля capability в YtDlpBackend; ядро и UI не меняются |
| Новый источник (сайт с прямыми mp4/HLS) | `Native`-бэкенд: resolve + переиспользование Generic Pipeline |
| Тесты | `FakeBackend` с программируемым поведением и сбоями |

## 5. Целевой бэкенд: YouTube через yt-dlp (Delegate)

### 5.1 Формат интеграции

yt-dlp поставляется как **portable standalone-бинарник** (~30 МБ, Unlicense — юридически чист для бандлинга). Взаимодействие — только через subprocess с машиночитаемым протоколом: **JSON на stdout, никакого экранного парсинга**. Версия компонента pinned; обновление — по регламенту §9.4.

### 5.2 Режимы вызова

| Режим | Назначение | Синтаксис (эскиз) |
|---|---|---|
| **R-1 Resolve** | метаданные для UI/выбора формата | `yt-dlp --no-config -J --skip-download [--flat-playlist] URL…` (батч до лимита cmdline; свыше — `--batch-file`) |
| **R-2 Delegate download** *(целевой)* | скачивание + муксинг целиком в yt-dlp | см. §5.3 |
| **R-3 Resolve-only** *(будущее, L2)* | только URL/headers потоков, качает Generic Pipeline | `--no-config --print` / `-J` без скачивания; активируется сменой capability |

Кэширование: `ResolvedMedia` в MetadataCache с TTL ≤ `expiresAt`; повторное открытие UI без повторного spawn; протухший кеш — тихий re-resolve, не ошибка.

### 5.3 Скеч целевой команды (R-2)

```
yt-dlp --no-config \
  --newline --no-simulate \
  --print after_move:filepath \
  --progress-template "dl:@P %(progress.downloaded_bytes)s %(progress.total_bytes)s %(progress.speed)s %(progress.eta)s %(info.id)s" \
  -f "<перевод политики качества, §5.7>" \
  -o "<staging_dir>/%(id)s.%(ext)s" \
  --ffmpeg-location "<bundled ffmpeg (LGPL-сборка)>" \
  --cache-dir "<appcache>" \
  --concurrent-fragments 4 \
  --no-part …(по политике) \
  <URL>
```

Контракт результата: финальный путь файла — из `--print after_move:filepath` (после муксинга/переименований); джоба завершается атомарным переносом из staging в библиотеку (§9.2).

### 5.4 Гигиена процессов (все spawn — через единый ProcessRunner, §9.1)

- **`--no-config` — обязательно всегда** (security: лежащий в CWD `yt-dlp.conf` позволяет инжект опций вплоть до `--exec` = RCE; см. §13).
- Окружение: whitelist переменных; **не наследовать** `PYTHONPATH`/`PYTHONHOME`; форс `PYTHONUTF8=1` (иначе в пайпы на Windows летит cp1251).
- CWD — контролируемый каталог приложения.
- Параллельная выкачка stdout **и** stderr (анти-дедлок на заполнении буфера), лимит на объём вывода.
- Отмена = **kill дерева процессов** (yt-dlp порождает ffmpeg-детей; на Windows — Job Object `KILL_ON_JOB_CLOSE`), затем чистка staging-каталога джобы.
- Таймауты на resolve-вызовы; fingerprint `--version` при старте (сверка с pinned).

### 5.5 Принятые издержки и меры

| Издержка | Мера |
|---|---|
| ~30 МБ бинарник | уже возим ffmpeg (~35–40 МБ LGPL); суммарно приемлемо |
| Spawn-латентность метаданных (0.5–3 с) | MetadataCache, батчинг URL, префетч при старте |
| AV false positives (PyInstaller one-file) | переподпись бинарника своим сертификатом, репорты вендорам, FAQ; pin+откат при проблемной версии |
| Обновления — наша зона ответственности | ComponentUpdater + телеметрия отказов с ключом «версия yt-dlp» → сигнал обновления (§9.4) |
| Схема `-J` не версионирована | defensive-маппинг (неизвестные поля игнорируются), contract-тесты на golden-JSON |

### 5.6 Маппинг ошибок yt-dlp → таксономия ядра

Exit-кодам yt-dlp **не доверяем**; классифицируем по stderr/JSON:

| Признак | Класс | Политика ядра |
|---|---|---|
| `Video unavailable` / приватное / удалено | `Fatal:NotFound` | стоп, диагноз пользователю |
| HTTP 403/410, протухшие URL | `UrlExpired` | re-resolve и продолжение |
| сетевые таймауты/сбросы | `NetworkTransient` | retry c backoff |
| `Sign in to confirm you're not a bot` и аналоги | `AntiBot:Blocked` | стоп; проверка обновления компонента; пользовательский сценарий (cookies/прокси) — M3 |
| ошибки формата/опций | `Config` | баг перевода политики — алерт разработчику |
| крэш/мусорный вывод | `ExtractorBroken` | телеметрия + «обновите компонент» |

### 5.7 Перевод политики качества

`FormatSelector` (§7) хранит пользовательские пресеты и для Delegate-бэкенда транслирует их в язык yt-dlp:

- «лучшее ≤1080»: `-f "bv*[height<=?1080]+ba/b[height<=?1080]"` (или `-S "res:1080"`);
- «только аудио»: `-f "ba/b"`;
- кодеки/контейнер — через `-S` (sort) как более выразительный механизм.

Один и тот же пресет для Native-бэкендов — просто выбор `Stream` из `ResolvedMedia`. UX качества единый для всех источников.

## 6. Бэкенд Rutube (Native)

- `capabilities: { resolve: true, download: Native }` — **существующий прототип мигрирует почти как есть**: его резолвер становится `resolve()`, HTTP-скачивание + ffmpeg-муксинг переезжают в Generic Pipeline как его первая battle-tested реализация.
- Rutube — «тихая мишень» (без активной антибот-эволюции): нативный скрейпер там живёт долго, оснований менять подход нет.
- **Немедленное действие (до начала переписывания):** записать golden-фикстуры с живого прототипа — пары «реальный HTML/JSON-ответ → эталонное `ResolvedMedia`». Это позволит валидировать миграцию на любой целевой стек без сети и станет основой contract-тестов (D8).

## 7. Ядро приложения

**Router.** Сначала pattern-match по `urlMatchers` зарегистрированных бэкендов; неоднозначность — опциональный probe; «источник не поддерживается» — внятная ошибка с возможностью «всё равно попробовать» (бэкенд-по-умолчанию/эксперименты — опция настроек).

**JobManager.** Жизненный цикл: `Created → Resolving → AwaitingStart → Downloading → PostProcessing → Finalizing → Completed | Failed | Cancelled | Paused`. Каждый переход — запись в append-only job journal; после крэша — восстановление очереди, resume недокачанного из staging (partial-файлы).

**Scheduler.** Одна очередь приоритетов; глобальный лимит активных джоб (2–3 по умолчанию) + **per-host лимит** (YouTube — 1–2 параллельных скачивания с IP). Pause/resume/«следующим» — операции над очередью.

**FormatSelector.** Пресеты качества («до 1080p, MP4, лучшее аудио» и т.п.) как данные; выдаёт либо `Stream[]` для Native, либо транслируется в `-f/-S` для Delegate (§5.7). Не содержит кода бэкендов.

## 8. Generic Download Pipeline (для `Native`-бэкендов)

1. Забор потоков по `Selection` (с headers из `Stream`).
2. HTTP-качалка: range/resume, throttling-aware, ретраи `NetworkTransient`; HLS — фрагменты с ограниченным параллелизмом; DASH — опционально (M3+).
3. **FfmpegService**: муксинг video+audio (copy по умолчанию), embed метаданных/обложек/субтитров/глав — по политике; прогресс из `-progress pipe:`; graceful kill.
4. Постобработка в staging → финализация (§9.2).

Ре-резолв при 403/протухании URL — обязанность пайплайна (сообщение с ядром через `UrlExpired`-политику).

## 9. Инфраструктура

**9.1 ProcessRunner** — единственная точка порождения процессов (yt-dlp, ffmpeg): гигиена §5.4, tree-kill, UTF-8, лимиты вывода, таймауты. Все процессы приложения — только через него.

**9.2 StagingFS** — временный каталог на джобу (по умолчанию рядом с целевой папкой — чтобы финализация была rename, а не копия через диск). Финализация = атомарный move + запись в Library/Registry. Отмена/крэш → чистка staging.

**9.3 MetadataCache** — `ResolvedMedia` + artwork с TTL; embedded-DB.

**9.4 ComponentUpdater** (критичен для D5): манифест (yt-dlp: pinned-версия, SHA256), собственный mirror, скачивание в staging, верификация, атомарный swap при рестарте, «known-good» для откката. **Не** полагаться на `yt-dlp -U` (права под Program Files). Телеметрия отказов агрегируется с ключом «версия компонента» → автоматический сигнал «выйшло обновление под текущую поломку».

**9.5 Хранилище** — embedded DB (SQLite-класс): jobs, job journal, library, downloaded-registry (дедуп, аналог `--download-archive`), settings.

```

## 13. Безопасность (чек-лист, обязательный к CI-ревью)

## 15. Маппинг на стек (ядро нейтрально, реализация дважды спроектирована)

| Компонент | Kotlin/JVM | Rust |
|---|---|---|
| JobManager / отмена | корутины, `SupervisorJob`, structured concurrency | tokio tasks + `CancellationToken` |
| Command/Event Bus | `Channel`/`SharedFlow` | `tokio::sync::mppc`/`broadcast` |
| Контракт Backend | `interface` | `trait` + `async_trait` |
| ProcessRunner | ProcessBuilder + JNA JobObject | `tokio::process` + `win32job` |
| Дерево процессов (Win) | JNA | `win32job` |
| Хранилище | SQLDelight | rusqlite / sqlx |
| Scheduler | `Semaphore` per-host | `tokio::sync::Semaphore` |
| Фронтенды | Compose Desktop (GUI) | ratatui (TUI) / egui / iced / Tauri (GUI) |
| Компоненты reuse | NewPipeExtractor/JavaTube как библиотеки (после лицензионного аудита) | rustypipe (проверить лицензию/bus factor) — кандидат на будущий Native-бэкенд YouTube |

Выбор стека не влияет на контракты, данные, формат golden-фикстур и регламенты этого документа. Фикстуры M0 переносятся между стеками без изменений.

## 16. Риски и меры

| Риск | Вероятность | Мера |
|---|---|---|
| Эскалация PO-токенов: yt-dlp потребует sidecar-провайдер (Node/Docker) для части клиентов | средняя, растёт | мониторинг issue-трекера yt-dlp; ротация клиентов через `--extractor-args`; решение о sidecar отложено до фактической необходимости (не закладывать в M1) |
| AV false positives | высокая | переподпись бинарника, pin+откат, репорты вендорам, FAQ |
| Схема `-J` дрейфует | высокая | defensive-маппинг + contract-тесты |
| Поломка Rutube-скрейпера | низкая | golden-фикстуры + телеметрия; при необходимости — Generic Pipeline легко дополнить правкой резолвера |
| Правовой вопрос скачивания с YouTube | константный | ортогонален выбору бэкенда (ToS запрещает любой инструмент); вопрос позиционирования продукта, не архитектуры |
| Зависимость от yt-dlp как проекта | низкая | собственный mirror бинарников; контракт Backend позволяет подмену |

## 17. Приложение: регламент работы с yt-dlp-компонентом

1. В поставке — pinned-версия + её SHA256 в манифесте приложения.
2. Приложение стартует → fingerprint (`--version`) → сверка с манифестом → рассинхрон = переустановка компонента из пакета.
3. Телеметрия отказов (класс ошибки × версия) → порог → приложение предлагает обновление (свой manifest/mirror) → SHA256 → staging → swap при рестарте → при росте ошибок после обновления — автооткат на known-good.
4. Обновление компонента **никогда не требует релиза приложения**. Обратное (смена формата `-J`, ломающая маппинг) отлавливается contract-тестами и требует минорного релиза бэкенда.

**Итог:** архитектура держится на четырёх несущих конструкциях — контракте `Backend` с capability-моделью (заменяемость загрузчиков как свойство системы, а не жест доброй воли), целевом YtDlpBackend в Delegate-режиме с процессной изоляцией и собственным каналом обновления, общем Generic Pipeline, принимающем миграцию вашего работающего Rutube-кода, и персистентном job journal со staging-моделью атомарной финализации. Всё остальное — детали реализации, заменяемые без пересмотра этого документа.
