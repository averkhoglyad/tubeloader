# Ядро Tubeloader и контракт SourceAdapter

## Problem Statement

Скачивать видео и аудио из нескольких источников можно только через прототип, где логика источника,
скачивание, муксинг и UI перемешаны в одном процессе и одном модуле. У прототипа рабочий только
Rutube-пайплайн, YouTube-экстракция мертва из-за антибота, а любая попытка починить источник требует
правок в общем коде и релиза приложения. Пользователь не может ни добавлять источники, ни терять
источник безболезненно, ни проверить поведение скачивания без сети и без GUI.

## Solution

Появляется headless-ядро, к которому фронтенды подключаются как тонкие клиенты: команды вниз,
события и состояния вверх. Ядро знает про источники только через контракт `SourceAdapter` и роутит
URL по декларированным адаптером шаблонам. Скачивание идёт через staging с атомарной финализацией,
прогресс и ошибки нормализуются ядром, операции над медиафайлами идут через порт `MediaTool`.

Адаптеры в эту спеку не входят: она фиксирует ядро и контракт как точку расширения. Rutube-адаптер
и yt-dlp-адаптер — отдельные спеки, каждая со своими contract-тестами на golden-фикстурах.

## User Stories

1. Как пользователь, я хочу вставить URL источника, чтобы приложение само поняло, какой адаптер его
   обслуживает, без выбора источника вручную.
2. Как пользователь, я хочу видеть внятную ошибку, когда URL не принадлежит ни одному источнику,
   чтобы понять причину, а не получить молчаливый отказ.
3. Как пользователь, я хочу вставить URL несуществующего видео, чтобы получить отдельное сообщение
   «видео не найдено», отличное от «источник не поддерживается».
4. Как пользователь, я хочу получить метаданные видео (заголовок, автор, длительность, обложка)
   до начала скачивания, чтобы решить, качать ли.
5. Как пользователь, я хочу выбрать качество из списка доступных вариантов, чтобы управлять
   размером и разрешением результата.
6. Как пользователь, я хочу отдельно выбрать только аудио, чтобы получить звуковую дорожку без видео.
7. Как пользователь, я хочу видеть прогресс скачивания, чтобы понимать, сколько ждать.
8. Как пользователь, я хочу видеть прелоадер, когда прогресс объективно неизвестен, чтобы не путать
   его с зависанием.
9. Как пользователь, я хочу отменить загрузку в любой момент, чтобы не тратить трафик и диск.
10. Как пользователь, я хочу, чтобы отменённая или упавшая загрузка не оставляла мусор в целевом
    каталоге, чтобы каталог оставался пригодным для просмотра.
11. Как пользователь, я хочу, чтобы файл появлялся в целевом каталоге только целиком, чтобы не
    открывать полуфайл и не путать его с готовым.
12. Как пользователь, я хочу видеть список текущих загрузок с их состояниями, чтобы следить за
    несколькими задачами одновременно.
13. Как пользователь, я хочу запустить несколько загрузок подряд, чтобы они шли, не блокируя друг
    друга и не блокируя интерфейс.
14. Как пользователь, я хочу видеть отдельный класс ошибки при обрыве сети, чтобы понимать, что
    проблема временная и загрузку можно повторить.
15. Как пользователь, я хочу видеть отдельный класс ошибки при поломке экстрактора источника, чтобы
    понимать, что дело в изменении на стороне источника, а не в моих действиях.
16. Как пользователь, я хочу задать целевой каталог, чтобы файлы попадали туда, где мне удобно.
17. Как пользователь, я хочу, чтобы у меня спросили подтверждение при перезаписи уже существующего
    файла, чтобы не потерять ранее скачанное.
18. Как пользователь, я хочу видеть состояние задачи после её завершения (готово / отменено /
    упало), чтобы понимать финальный исход.
19. Как пользователь, я хочу, чтобы закрытие приложения не оставляло полуфайлов и зависших
    процессов-инструментов, чтобы система оставалась чистой.
20. Как разработчик, я хочу тестировать поведение ядра без сети и без GUI, чтобы иметь быстрые
    детерминированные тесты.
21. Как разработчик, я хочу добавить источник, не правя ядро, чтобы новые источники появлялись без
    регрессий в существующих.
22. Как разработчик, я хочу, чтобы каждый адаптер прогонялся через один и тот же набор
    contract-тестов на golden-фикстурах, чтобы замена реализации не меняла поведение незаметно.
23. Как разработчик, я хочу, чтобы ошибки и прогресс от разных адаптеров приходили в ядро в единой
    форме, чтобы UI не разрастался ветками по источникам.
24. Как разработчик, я хочу подменять инструмент над медиафайлами фейком в тестах ядра, чтобы
    тестировать оркестрацию без запуска внешних процессов.
25. Как разработчик, я хочу, чтобы внешние CLI-инструменты запускались в отдельном процессе, чтобы
    падение или зависание инструмента не роняло приложение.
26. Как разработчик, я хочу собирать приложение под Windows как целевую платформу M1, чтобы
    проверить рабочий сценарий end-to-end на своей машине.

## Implementation Decisions

**Ядро и фасад.** Ядро — Kotlin/JVM, headless: без зависимостей от UI-фреймворка. Граница с
фронтендом — фасад команд (разбор URL, загрузка метаданных, постановка загрузки, отмена) и
наблюдаемые состояния. Ядро владеет состоянием: список загрузок отдаётся как
`StateFlow<Map<TaskId, DownloadState>>`; фронтенд собирает его через `collectAsState` и не держит
собственной копии. Фронтенд не входит в эту спеку.

**Контракт SourceAdapter.** Единый интерфейс, никакой трёхконтрактной схемы. Операции:

- разбор URL → `FindResult.Found(id)` | `Unsupported` | `NotFound`: отдельные исходы, не исключения;
- загрузка метаданных по идентификатору → `NotFound` | `Found(VideoMeta)`: исхода `Unsupported` тут нет,
  так как поддержка уже определена на разборе URL;
- `downloadVideo(id, quality, targetPath)` и `downloadAudio(id, quality, targetPath)`: отдельные
  операции, а не один вызов с флагом вида.

Capability-модель — через опрос адаптера: `Delegate` (адаптер скачивает сам), `Native` (скачивает
общий пайплайн ядра), `ResolveOnly`. Роутинг — по декларированным адаптером URL-паттернам, без
сетевых проб. Неоднозначный матч нескольких адаптеров — ошибка, а не выбор первого.

**Входные сценарии.** UI предусматривает оба входа: URL целиком и отдельно id плюс выбор источника
из списка. Контракт обслуживает оба.

**DownloadState.** Расширяемый sealed-набор состояний одной загрузки, отдаваемый как Flow. Набор
покрывает жизненный цикл (ожидание, метаданные, скачивание, финализация, завершено, отменено,
ошибка) и оставляет слот под состояния прерывания для проверок, требующих действия пользователя
(например, cookies или сессия). Слот проектируется как часть механизма прерываний, а не как набор
частных состояний под конкретный источник.

**Progress.** Нормализованная мера продвижения: `Indeterminate` (прогресс неизвестен, например при
перекодировании) или `Determinate(current, total)`. Адаптер отдаёт свои сырые форматы, ядро
нормализует.

**MediaTool.** Порт ядра для операций над медиафайлами: инициализация инструмента, запуск, прогресс.
Параметры операции задаёт адаптер, потому что только адаптер знает, что делать: раздельные
потоки audio+video и муксинг у одного источника против HLS-плейлиста эпизодов с конкатенацией и
remux без перекодирования у другого. Сам инструмент адаптер не инициализирует — это делает ядро
через порт. Порт закрывает ядро от конкретного инструмента и позволяет подменять его фейком в
тестах.

**Форма VideoMeta и Quality.** `VideoMeta` — идентификатор, заголовок, автор, длительность,
обложка, доступные качества. `Quality` — один доступный вариант видео или аудио, выбирается
пользователем. Модель единая для всех источников; модели конкретных источников наружу не протекают.

**Staging и финализация.** Скачивание идёт в видимый партиал `<target>.part-<id>` в каталоге
назначения (индустрия-стиль, yt-dlp/браузеры); в целевом каталоге не бывает полуфайлов с
финальным именем. Ядро создаёт пустой партиал и владеет им; адаптер наполняет его и не знает
его судьбы; свои промежуточные файлы адаптер порождает и чистит сам (structured concurrency
гасит их вместе с задачей). Финализация атомарна: `Files.move(part → target, ATOMIC_MOVE)` в
том же каталоге. Отмена и падение удаляют партиал ядра. Поведение при существующем целевом
файле — прерывание задачи в обобщённый слот `Interrupted(PendingInteraction)` с запросом
подтверждения (`OverwriteConfirmation`), а не молчаливая перезапись; проверка на старте и
повторная перед move (файл появился за время скачивания → снова прерывание). Отказ от
перезаписи → `Cancelled` + cleanup. Будущие типы прерываний (cookies, сессия) ложатся в тот же
слот без слома API.

**Очередь и параллелизм.** Ядро поддерживает несколько одновременных загрузок, чтобы UI не был
последовательным. Постановки идут через единую очередь FIFO: сверх лимита задачи ждут, при
освобождении слота стартует старейшая; приоритетов и пауз нет. Лимит один, глобальный, живёт в
конфигурации приложения: дефолт 3, минимум 1, ноль — невалидное значение, при котором ядро берёт
дефолт; per-source лимитов в M1 нет, лимит считает задачи, а не их внутренние потоки. Очередь
владеет жизненным циклом задач: единственное место, где меняется их состояние; наружу — StateFlow
фасада. Модель конкурентности — конфайнмент всех мутаций на одном воркере без общих мутабельных
структур и блокировок (ADR-0003). Смена лимита в рантайме без преемпции: подняли — ждущие
стартуют, опустили — бегущие доезжают, новые слоты не выдаются до входа в лимит. Отдельная
очередь для MediaTool не вводится: лимит задач ограничивает и параллельные запуски инструмента.

**Изоляция.** Единственная форма процессной изоляции, закладываемая сейчас, — внешние CLI-инструменты
в отдельном процессе. Экстракторы в этой спеке и в Rutube-адаптере работают внутри процесса
приложения.

**Роль прототипа.** Логика `rutube.kt` (resolve → m3u8 → сегменты → remux) и муксер из
`YoutubeVideoService` (параллельная загрузка audio и video, взвешенный прогресс по contentLength,
ffmpeg с копированием потоков) переносятся как референс с переписыванием под целевую архитектуру,
не копипастой. Ключевая форма, переносимая из прототипа в ядро, — взвешенный прогресс двух
параллельных потоков: доли audio и video по длине контента, скачивание занимает большую часть
шкалы, финальный муксинг — остаток.

**Внешние инструменты.** Запускаются в отдельном процессе; дерево процессов убивается целиком при
отмене, иначе остаются осиротевшие дочерние процессы.

**Раскладка репозитория.** Текущий прототип (TornadoFX+JavaFX, `MainKt` как точка входа, зависимости
на Java-обёртку YouTube-загрузчика и JAVE) этой спекой не поддерживается: приложение переписывается,
точка входа и сборка переезжают на новый стек. Порядок и способ сноса прототипа — отдельный тикет.

## Testing Decisions

Хороший тест проверяет внешнее поведение через публичный шов и не зависит от деталей реализации:
никаких проверок приватных методов, никаких ассертов на структуру внутренних файлов staging, кроме
наблюдаемого факта «в целевом каталоге нет полуфайлов».

Швы, в порядке предпочтения:

1. **Фасад ядра (главный шов).** Команды внутрь, `StateFlow` наружу, поверх FakeSourceAdapter и
   FakeMediaTool. Здесь живёт большинство тестов: роутинг URL по шаблонам, неоднозначный матч,
   исходы «не поддерживается» и «не найдено», жизненный цикл состояний, отмена, нормализация
   прогресса, поведение при существующем целевом файле, параллельные загрузки.
2. **Контракт SourceAdapter.** Один переиспользуемый набор contract-тестов, прогоняемый каждым
   адаптером. Вход — golden-фикстуры: записанные ответы источника и эталонные `VideoMeta` / список
   `Quality`. Здесь же проверяются исходы разбора URL. Прогон обязателен при любом изменении
   реализации адаптера.
3. **Порт MediaTool.** Фейк в тестах швов 1–2; настоящий инструмент — только в тестах адаптера, на
   маленьких медиафайлах, с проверкой прогресса и отмены.

Стек тестов: kotest + mockk для unit-тестов, платформа JUnit6 (`useJUnitPlatform()` включён в
`:core` тикетом 01). Предыдущий артефакт для тестов ядра — `FakeBackend` из
`docs/research/report-1.md` §14; форма входа (детерминированные, программируемые сбои по классам
ошибок) переносится.

### Правила оформления тестов

**Контекст — тестируемый метод.** Класс теста наследует `FreeSpec`. Первый уровень вложенности —
тестируемый метод, второй и глубже — проверяемые кейсы этого метода. Один метод — один блок, кейсы
не размазываются по классу. Имя кейса описывает наблюдаемое поведение, а не вызов; внутри кейса —
секции `// given`, `// when`, `// then`.

```kotlin
class MailSendServiceTest : FreeSpec({
    "send" - {
        "throws IllegalArgumentException if no receiver email" { }
        "creates MailMessage and pass to MailSender" { }
    }
})
```

Вложенность глубже двух уровней допустима, когда у метода есть осмысленные группы поведения.

**Данные генерируются, а не выдумываются.** `Gen<T>` — тип параметра генератора, конкретные
реализации — `Arb` (случайные значения) и `Exhaustive` (перебор). Генераторы живут в отдельном
`gen.kt` рядом с тестами и оформляются как расширения `Arb.Companion`:

```kotlin
fun Arb.Companion.userEntities(
    ids: Gen<UUID?> = Exhaustive.of(null),
): Arb<UserEntity> = Arb.bind(ids, Arb.string()) { id, name -> UserEntity(id, name) }
```

Составные значения собираются через `Arb.bind(...)`, а не через `randomUUID()` и литералы; прогон —
`checkAll(gen) { ... }`, один сэмпл — `gen.next()`. Жёсткие литералы остаются только там, где
значение проверяется как ожидаемое, а не как вход.

**Конфигурация kotest.** Класс конфига в kotest 6 ищется по fully qualified name, а не сканированием
classpath, — сканирование выключено в самом фреймворке. Поэтому в `src/test/resources/kotest.properties`
каждого тестового модуля может стоять только выбор конфига, а не отключение скана:

```properties
kotest.framework.config.fqn=<fqn>
```

Порядок резолвинга конфига в kotest 6: класс `io.kotest.provided.ProjectConfig`, затем FQN из
`kotest.framework.config.fqn`, затем класс `ProjectConfig` в общем пакете всех тестов. Отдельного
файла `kotest.properties` модулю достаточно, когда нужен именно явный FQN; `ProjectConfig` в общем
пакете работает без всякой конфигурации.

**Моки: query-методы против command-методов.** Разделение по роли метода, а не по типу класса.

Query-метод возвращает значение: достаточно заглушить принимаемое и возвращаемое значение и
проверить результат. Вызов такого метода **не верифицируется** — он средство, а не предмет
проверки:

```kotlin
// правильно: заглушка + проверка результата
val actual = service.load(id)
actual shouldBe entity

// неправильно: findById — query-метод, его вызов верифицировать не нужно
verify { repository.findById(eventId) }
```

Command-метод меняет состояние системы: заглушка принимает любой аргумент, после вызова идёт
`verify` с захватом, и захваченный реальный аргумент сравнивается с ожидаемым:

```kotlin
// правильно: перехват реального аргумента и сверка с ожидаемым
val slot = slot<SimpleMailMessage>()
verify { emailSender.send(capture(slot)) }
slot.captured shouldBeSameInstanceAs mailMessageForSender

// неправильно: проверка «факта вызова» без сверки того, что реально передано
verify { emailSender.send(any()) }
```

Захваченный аргумент сверяется с ожидаемым значением, а не с тем же моком.

**Очистка состояния — флоу-методами.** Моки и прочее состояние чистятся в `afterTest`, `afterEach`,
`beforeTest`, `beforeSpec`, а не вручную в каждом кейсе:

```kotlin
class MailSendServiceTest : FreeSpec({
    afterTest { clearAllMocks() }
})
```

Ручная очистка внутри кейса — исключение, оправданное только когда тест проверяет поведение между
вызовами.

## Out of Scope

- Фронтенды: Compose Desktop, CLI, TUI. Слой презентации разделён по фронтендам и тестируется
  отдельно от ядра.
- Конкретные адаптеры: Rutube Native и yt-dlp Delegate — отдельные спеки со своими фикстурами.
- Собственный InnerTube-клиент, обход антибота, cookies, прокси, PO Token, impersonation.
- Обновление внешних компонентов и телеметрия отказов (ComponentUpdater из `report-1.md` §9.4).
- Job journal, восстановление очереди после падения, возобновление недокачанного.
- История и индекс загрузок, дедуп «уже скачано»: в M1 ядро ведёт только текущую сессию.
- Субтитры, главы, обложки как отдельные артефакты; плейлисты и каналы.
- Приватные видео и любые формы аккаунтов; поддерживаются только public и unlisted.
- DASH как отдельная ветка пайплайна.
- Упаковка дистрибутива (jpackage против gradle distribution) — детали вынесены в тикет сборки.
