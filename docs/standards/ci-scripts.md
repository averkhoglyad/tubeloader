# CI-скрипты: зоны ответственности

Источник истины по разграничению CI-скриптов на слои. Разделение не зависит от CI-провайдера.

- `scripts/weeek/` — интеграция с Weeek API: составляет сообщения и отправляет их. Читает только
  свой конфиг рядом со скриптом.
- `scripts/ci/` — сбор данных, не зависящий от провайдера: диапазон коммитов, авторы, номера
  задач. Конфиг свой, рядом со скриптами.
- `.github/scripts/` и `.gitverse/scripts/` — оркестрация флоу провайдера и всё
  платформо-специфичное. Конфиги лежат рядом со скриптами.
- Провайдерский скрипт тонкий: собирает runtime-данные события, передаёт их значениями и
  делегирует вызовы в `scripts/ci` и `scripts/weeek`. Логики сбора данных и доменной логики в нём
  нет.
- Логика не дублируется между провайдерами. Допустимое дублирование — вызов общего скрипта с
  передачей значений.
- Провайдерский слой не читает конфиги других слоёв.
- Домен не знает, кто его вызвал: хост ссылок и адреса приходят снаружи. Провайдерский конфиг
  обязан задать ключи, которые домен читает из окружения (`webBase`, `branchPath`, `prPath`); без
  них домен завершается ошибкой.
- Платформенные данные, обогащающие сообщение (ссылки, профиль автора), вычисляются в
  провайдерском слое через оркестрацию, а не внутри общего скрипта.
- Добавление нового провайдера: конфиг рядом со своим адаптером, адаптер-обёртка, воркфлоу. Правок
  в `scripts/ci/` и `scripts/weeek/` быть не должно.

## Как проверяется

`grep`-пробами: в провайдерском слое не встречается `git log` и нулевой sha; общие слои не знают
имён провайдеров и хостов; провайдерский слой не ссылается на чужие конфиги.
